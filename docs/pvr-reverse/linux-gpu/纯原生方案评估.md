# 图形栈路线评估与决策记录（Redmi 9A / MT6765 / PowerVR GE8320）

- 设备：Redmi 9A（dandelion，MT6762G，GPU BVNC `22.87.104.18`，Rogue 8XE）
- 内核：mainline 7.1 + 厂商 PowerVR DDK `1.13@5776728`（`pvrsrvkm.ko`，零绕过完成 FW 启动/KCCB/上下电）
- 用户态：Ubuntu 24.04（glibc 2.39），phoc/wlroots 0.17
- 版本：2026-11-24 第二版（**已含实机结论：路线 A 证伪**）

---

## 0. 结论

| 路线 | 状态 | 说明 |
| --- | --- | --- |
| A. TI glibc UM + BVNC 补丁 | **已证伪，关闭** | 实机打穿两关，第三关撞在编译期结构体 ABI（`RGXFWIF_CMD3D` 352 vs 320），不可绕过 |
| B. libhybris | 备选 | 只替换 ABI 层，**不改善性能**，工作量比"数天"更大 |
| **C. 现有 UM + 性能优化** | **当前主线** | 用户态本就是正确 BVNC 的同源库；收益来自 fence 与 buffer 路径 |
| D. 主线 `drm/imagination` + Mesa pvr | 阻塞 | 缺 8XE 的主线格式固件，无法启动 |

**结论：不存在"零壳"的现实解；现有方案就是这类设备在 Linux 上的标准解（且比 libhybris 更薄）。精力应全部转到 C。**

## 1. 路线 A 的实机结果（决定性证据）

### 1.1 三道门

| 关卡 | 现象 | 结果 |
| --- | --- | --- |
| 1. UM `CompatibilityCheck` | 打补丁前 `PVRSRV_ERROR_BVNC_MISMATCH` → 打完 3 条指令后变成 `PVRSRV_ERROR_BVNC_UNSUPPORTED` | 可绕 |
| 2. UM 编译期特性表 | `libsrv_um.so` 内 `0x59a18` / `0x5a0b0` 两张表（15/18 个目标核，不含 22.87.104.18）；从 MTK 同版本 UM 抄入两条 56 B 表项后通过 | 可绕 |
| 3. FW/UM 结构体对齐 | `RGXAlignmentCheck: size/offset mismatch in RGXFW_ALIGN_CHECKS_INIT[21] between UM(352) and FW(320)`（`rgxinit.c:1865`） | **硬阻塞** |

### 1.2 根因

`include/rogue/rgx_fwif_alignchecks.h:90-92`：

```c
/* RGXFWIF_CMD3D checks */
sizeof(RGXFWIF_CMD3D),
offsetof(RGXFWIF_CMD3D, s3DRegs),
```

- 索引 [21] 校验的就是 `sizeof(RGXFWIF_CMD3D)`
- TI UM（22.104.208.318）：**352 B**；本机固件（22.87.104.18）：**320 B**
- 差值来自 `s3DRegs` 的寄存器数组长度——由 BVNC 决定，属**编译期 ABI**
- 该校验由内核逐项比对 UM/FW 数组强制执行，运行时无法修补

### 1.3 结论与教训

- **"UM 与 BVNC 无关"不成立**：即使绕过 1、2 两关，3D 命令包大小/寄存器布局仍与固件不一致。
- 方法论教训：用"扫描常量/字符串"判断库是否与 BVNC 相关是不可靠的；BVNC 依赖藏在结构体尺寸与寄存器表长度里。
- 设备端已清理 `/opt/pvr`，日用 `phoc-pvr` 未受影响。

（失败记录：`notes/failures.md` F-001）

## 2. 为什么"零壳"没有先例

### 2.1 别人的两条合法路径

| 路径 | 例子 | 成立的前提 |
| --- | --- | --- |
| 厂商 glibc BSP | TI AM62/J721E、NXP i.MX、Renesas R-Car、早年 Intel Atom(SGX) | 厂商针对**那颗 BVNC**同时发 glibc UM |
| 主线 `drm/imagination` + Mesa `powervr` | StarFive JH7110(BXM-4-64)、TI AXE/AM62 | IMG 为那颗 BVNC 发布**主线格式固件**（linux-firmware） |

跑 Android 闭源驱动的 Linux 发行版（Ubuntu Touch / Sailfish / Halium）全部使用 **libhybris**——也就是"套壳"，只是比我们厚。

### 2.2 没有"跨 BVNC 移植闭源 UM"的先例

原因就是 §1.2：换 BVNC = 换 UM 构建，改表/改校验都不行。全世界没有人做成过，不是没人试。

MT6765 的 Linux BSP 未公开发布（联发科不发），所以"该 BVNC 的 glibc 原生包"现实中不存在。

## 3. 现有这层壳的定位

| 方案 | 每次 GL 调用开销 | 需要维护 | 备注 |
| --- | --- | --- | --- |
| Android 原生 | 0 | 无 | 用户态整体是 Android |
| **现有方案** | **0（`libGLESv2.so.2` 直接链接厂商库）** | 4 处 libc ABI + ELF 补丁 | 已验证出图 |
| libhybris | ≈0 | bionic linker/libc + 属性服务 + gralloc 适配 | 更厚 |
| Waydroid/容器 | 高 | 整层 Android | 不适合做桌面 |

本质：**补 libc ABI，不是模拟 GPU 驱动**。它等价于"自建一个最薄的 BSP 适配层"。

## 4. 路线 C：执行计划（当前主线）

### 4.0 先测（5 分钟）

```sh
PVR_GL_FLUSH_IS_FLUSH=1 phoc-pvr     # glFlush 恢复为真 flush
```

- 帧率/延迟明显改善 → 主因是 `glFinish`，先做 C1
- 基本无变化 → 瓶颈在 buffer 带宽，先做 C2

同时留基线：`glmark2-es2-wayland` 或 `es2gears_wayland`。

### 4.1 C1：`glFinish` → native fence（0.5~1 天）

DDK 能力齐备：`EGL_ANDROID_native_fence_sync`、`eglCreateSyncKHR`、`eglDupNativeFenceFDANDROID`、`PVRSRVFenceExportI`。

| 方案 | 做法 | 代价 |
| --- | --- | --- |
| 1（先验证收益） | 保存上一帧 fence，同一 `gbm_bo` 复用时 `eglClientWaitSyncKHR(fence, 0, 0)` | 不改 wlroots |
| 2（正规） | `eglDupNativeFenceFDANDROID` 得到 fd → atomic commit `IN_FENCE_FD` | 需给 wlroots 打小补丁 |

注意：`eglCreateSyncKHR(NATIVE_FENCE)` 前必须先 `glFlush`；fd 在 commit 后 `close`。

### 4.2 C2：buffer 路径（1~2 天，收益可能最大）

1. `MODE_CREATE_DUMB` → `/dev/dma_heap/system`（真 dma-buf）
2. 反汇编 `gralloc.rogue.so` 的 `MTKGenericAlloc`（内部含 `FBCSurface num tiles`），让分配走它，启用 tiling/压缩
3. 确认合成是 FBO 直写 scanout dma-buf，无 CPU 中转

### 4.3 C3：`gbm_surface`（依赖 C2）

基于同一分配器实现标准交换链；DDK 已广告 `EGL_EXT_buffer_age` / `EGL_KHR_partial_update`，可进一步省填充率。

### 4.4 C4：`bmemcp/bmemst` 128 B 向量化（0.5 小时，顺手）

收益小，不作为主线。

### 4.5 验收判据

| 检查点 | 成功判据 |
| --- | --- |
| C1 | 帧率提升且无花屏；`PVR_GL_FLUSH_IS_FLUSH=1` 与默认的差值消失 |
| C2 | 带宽受限场景（全屏填充）帧率提升；`modifier` 非 LINEAR 或 dma-heap 生效 |
| C3 | wlroots 走标准交换链，无 `gbm_surface` 报错 |
| 整体 | `glmark2-es2-wayland` 相比基线提升，且连续运行 30 分钟无超时/花屏 |

## 5. 路线 B（备选，暂不投入）

- 收益：去掉 ELF 补丁与 libc 垫片，改为标准 bionic 运行时。
- 代价：bionic linker/libc/属性服务/gralloc 适配；wlroots 仍需 GBM 桥（libhybris 不提供）。
- **不改善性能**：`glFinish`、dumb buffer、缺 `gbm_surface` 三件事一件都不会变。
- 触发条件：垫片维护成本变得不可接受，或有其他项目需要复用 bionic 运行时。

---

## 6. 路线 D（阻塞，不投入）

| 环节 | 证据 | 结论 |
| --- | --- | --- |
| 内核设备表 | `pvr_device.c:533-537` 仅 3 个 BVNC | 可绕过：`exp_hw_support=1`、`gpuid=` 覆盖（`:584`） |
| 固件 | 名字按 BVNC 生成（`pvr_device.c:348`）；`MODULE_FIRMWARE` 只登记 3 个（`pvr_drv.c:1533-1535`） | **硬阻塞**：无 22.x 主线格式固件；DDK 1.13 的 MIPS `rgx.fw` 不兼容 |
| 设备特性 | quirks/enhancements/features 由固件携带（`pvr_device_info.c`） | 没有 FW 就没有特性表 |

等 IMG 发布 8XE 的主线固件才有意义。
